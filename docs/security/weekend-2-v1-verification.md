## Confirmed findings and minimal remediations

**W2-01 — High, inactive local account can re-enter through exchange (fixed).** In [`auth_handlers.go`](../../apps/evt-api-go/internal/httpapi/auth_handlers.go), `issueAuthExchangeResponseForKratosIdentity` previously returned only `id, role` from the upsert and minted a session regardless of `domain_users.status`. `HandleAuthRefresh` already rejected inactive accounts, but exchange bypassed that control whenever Kratos authentication remained valid. Reproduction: exchange, set the synthetic local account to disabled, then exchange again. The fix reads and checks status within the existing transaction; both exchange handlers return `403 account_inactive`. No role or session is created for the disabled account. Tests: `TestSecurityPostgresInactiveAccountCannotExchange`, including native/web HTTP responses. Active-provider checks are also tested for both paths; the provider's existing non-200 rejection already mitigates ordinary invalid Kratos sessions.

**W2-02 — High, unauthenticated evidence upload capabilities (authentication fixed; case authorization still blocked).** [`router.go`](../../apps/evt-api-go/internal/httpapi/router.go), now `registerEvidenceRoutes`, previously registered four evidence routes directly on the net/http mux, bypassing global Gin authentication. `HandleEvidenceInit` in [`handlers_evidence.go`](../../apps/evt-api-go/internal/httpapi/handlers_evidence.go) can create a signed PUT URL with configured storage credentials. Existing file-count/MIME/declared-size and ID validation do not authenticate the caller. All four paths and aliases now use the existing `RequireAuth`; missing/invalid bearer tokens return 401 before invoking handlers. `TestEvidenceRoutesRequireAuthentication` verifies the actual registration helper used by production.

**W2-03 — High, refresh can survive a concurrent logout (fixed).** [`refresh.go`](../../apps/evt-api-go/internal/httpapi/refresh.go), `HandleAuthRefresh`, locked only the incoming token and never read `auth_sessions.revoked_at`. [`logout.go`](../../apps/evt-api-go/internal/httpapi/logout.go), `HandleAuthLogout`, updated the token family before updating the session without first taking the common session lock. A rotation inserting after logout's token-update snapshot can leave a current token in a revoked session. Serializable refresh transactions alone do not serialize a read-committed logout on the same session boundary. Both operations now lock the session before token mutations; refresh rejects revoked sessions. Logout also explicitly checks update errors (the existing PostgreSQL transaction/commit failure already prevented success after a failed statement). Real-database tests cover rotation, reuse revocation, idempotent logout, independently revoked sessions, and ten concurrent logout/refresh attempts. Serialization conflicts may still produce a fail-closed 500; no API retry semantics were changed.

**W2-04 — High, credential-controlled internal HTTPS requests (fixed).** [`verification_outcome.go`](../../apps/evt-api-go/internal/httpapi/verification_outcome.go), `verifySDJWTVCOutcome`, instantiated the default `IssuerMetadataResolver`, which fetches unverified `iss` metadata and `jwks_uri`. In [`issuer_metadata.go`](../../apps/evt-api-go/internal/credential/sdjwtvc/issuer_metadata.go), `validateURL` requires HTTPS and validates redirects but does not restrict destination networks. A valid credential signature is not required before key retrieval. An authenticated caller could therefore trigger internal HTTPS GETs; normal TLS certificate validation limits readable responses but does not prevent internal connection attempts. The runtime resolver now uses [`issuer_http.go`](../../apps/evt-api-go/internal/httpapi/issuer_http.go): public-address checks at actual dialing, pinned resolved IPs, blocked private/loopback/link-local/shared/reserved/translation ranges, no environment proxy bypass, and the existing HTTPS/redirect/timeout/response-size/TLS checks. Tests verify literal, mapped IPv4, IPv6 and DNS-localhost rejection, public-address classification, and rejection through the real metadata resolver before TLS. No internal production address was probed. Custom DNS routing/enterprise proxy requirements must be considered before deployment; library test clients remain injectable as before.

**W2-05 — High configuration exposure, Kratos admin published to all host interfaces (fixed in source).** [`docker-compose.yml`](../../apps/evt-api-go/docker-compose.yml), `services.kratos.ports`, published `4435:4435`. No authentication proxy/control for that binding is defined in this configuration. Host firewalls could mitigate actual exposure; their presence is unknown, and no live exposure is claimed. The minimal change binds `127.0.0.1:4435:4435`, retaining local operator/container-network access. Compose parsing confirms the loopback binding. Ory advises keeping admin endpoints private; see [Ory's security guidance](https://www.ory.com/docs/oel/console-lite/security).

**W2-06 — Potentially High credential exposure (current-tree remediation; operational verification outstanding).** [`infra/kratos/kratos.yml`](../../infra/kratos/kratos.yml) contained a literal database username/password DSN. Its value is intentionally omitted here and was never used or tested. Compose already overrides it with `DSN` for both Kratos processes, so deleting the fallback retains the existing environment-based deployment contract. Existing key and selected-pattern scans did not establish safety for this configuration. Operator action: determine privately whether the credential was valid or reused; rotate affected credentials if necessary and verify dependent services under the existing deployment authorization process. It remains in Git history; no history rewrite is proposed.

**W2-07 — Medium, unbounded JSON body allocation (fixed).** Auth exchange/refresh/logout and Gin handlers decoded bodies without a byte cap; the existing verification handler alone enforced 1 MiB. Read timeouts bound duration, not total allocation. `withRequestLimit` in [`middleware.go`](../../apps/evt-api-go/internal/httpapi/middleware.go) now applies the same 1 MiB cap around the router. Tests confirm reads stop at that bound. Existing decoder error contracts remain; oversized bodies may return the handler's existing 400 error rather than introducing a new response schema. Legitimate JSON requests larger than 1 MiB are now rejected; evidence bytes continue to go directly to storage.

## Unresolved release blockers: no speculative authorization policy

**W2-B1 — High, cross-employer reading and signed attestation issuance.** Affected endpoints:

- `GET /v1/employer/requests?employer_id=...`
- `GET /v1/employer/requests/{request_id}?employer_id=...`
- `POST /v1/employer/requests/{request_id}/attest`

Evidence: `AccessClaims` in [`claims.go`](../../apps/evt-api-go/internal/auth/claims.go) contains subject and global roles but no employer assignment. `GinRequireRole(RoleHRReviewer)` in [`routes.go`](../../apps/evt-api-go/internal/evt/routes.go) checks only that role. `EmployerHandlers.List/Get/Attest` in [`handlers_employer.go`](../../apps/evt-api-go/internal/evt/handlers_employer.go) accept the employer ID from the caller. `Repo.EmployerList/EmployerGet/EmployerAttestServerSigned` in [`repo.go`](../../apps/evt-api-go/internal/evt/repo.go) filter by that supplied ID, never authorize the HR subject against it. `employerHRPersonID` is used in the signed payload and audit event, not as an authorization predicate.

Inspected the identity JSON schema, authentication claims and role handling, `internal/db/store.go`, all repository SQL migrations (authority tables only), employer endpoints, and existing access-control documentation. No authoritative HR-to-employer assignment was found. The user also could not confirm one. Production legacy DDL and any RLS policy are unavailable, so this is an application-level finding demonstrated on local runtime fixtures, not a claim about inspected production RLS.

`TestReleaseBlockerEmployerScopeEvidenceAndLocalSigning` reproduces all three routes returning HTTP 200 for an unrelated global HR principal and stores a cryptographically valid employer-B attestation. Existing role gates stop requestors and unauthenticated users, and workflow state/row locking prevent invalid transitions; neither limits which employer a valid HR principal may act for.

Required decision: identify or establish the authoritative HR-principal-to-employer assignment and its provisioning/revocation rules, decide whether any explicit global reviewer privilege exists, then enforce that relationship consistently on list/get/attest before data disclosure or signing. Do not use caller IDs, email-domain guesses or key possession as permission. This decision and its integration tests are required before release; no speculative policy was implemented.

**W2-B2 — High, case-scoped evidence writes are not authorized.** `HandleEvidenceInit` never checks caller-to-case/check permission or persists the required caller-owned upload session. `HandleEvidenceComplete` returns 501 because persistence is absent. [`v1-evidence-upload.md`](../api/v1-evidence-upload.md) explicitly requires identity-based case policy and caller-owned upload sessions. This is an existing specification gap, not an inferred requirement for a new framework.

`TestReleaseBlockerEvidenceCaseScope` uses only synthetic storage credentials and offline AWS presigning: an unrelated authenticated requestor obtains an upload URL for arbitrary `case-b/check-b` (HTTP 200), without any database/case relationship. No upload or storage network request is made. The response's declared-size check is also not proof of storage-side byte-size enforcement. UUID object names, private ACLs, MIME/count checks and the newly required access token mitigate some abuse but do not establish case permission or complete the upload lifecycle.

Required decision: use an authoritative existing case access policy and persistence model, or explicitly authorize disabling the unfinished upload boundary for V1. Implementing an invented membership model or silently disabling the API was outside this assignment. Authentication remediation alone does not resolve this blocker.

The two `TestReleaseBlocker...` tests intentionally **pass when the documented gap is reproduced**. They are evidence collection, not authorization acceptance tests. Replace them with deny/allow authorization regressions when the policy is decided. Do not interpret their passing status as security acceptance.

## Local signing and remaining live verification

`TestReleaseBlockerEmployerScopeEvidenceAndLocalSigning` exercises real Gin middleware/route registration, employer handler, transaction, repository state change, `NewAttestationSignerFromPEMPath`, `SignAttestationJWS`, stored JWS, `NewStaticJWKSResolver`, and `Profile.VerifyAndNormalize`. The temporary PEM is RSA-3072, mode 0600, inside `t.TempDir`; its basename determines the test kid. The matching JWKS exists only in memory. The test rejects wrong public-key material with the same kid, an unknown kid, and a modified signed payload.

**What this proves:** local issuance/storage/signature-verification functionality on production code paths with synthetic inputs. **What it does not prove:** the production key's runtime accessibility, live issuance, employer authority, status/liveness, runtime HTTP legacy-verifier wiring, or production schema compatibility.

A concrete compatibility limitation was observed: `AttestationClaims.ResponseBody` is `[]byte`, so JSON marshaling signs it as a base64 string. The legacy normalizer expects an object (`json.RawMessage`) and reports `LEGACY_RESPONSE_BODY_INVALID`; signature evidence can still be valid. The test explicitly records this limitation. It was not changed because silently altering the frozen signed payload/claim contract is outside this remediation. Existing envelopes also lack portable expiry/status evidence. Runtime legacy HTTP verification stays explicitly unknown, and trust is never promoted from signature validity. A complete usable verification claim requires a separately approved compatibility decision.

Smallest human-operated follow-up, **not executed**:

1. After the release blockers and operational prerequisites are resolved, an authorized operator uses an already-approved synthetic/staging request and a properly assigned reviewer. Prefer staging with the equivalent release configuration and a staging key first.
2. For production-key verification without creating attestations or changing data, inspect one existing, explicitly approved non-sensitive artifact issued after rotation. Confirm protected `alg=RS256` and `kid=issuer-prod-2026-10`; verify its exact compact bytes against the stable public JWKS with strict algorithm/kid selection. Export only the approved public artifact/result; never retrieve the private PEM. Do not trust an historical demonstration key.
3. This can confirm an existing artifact, not prove a new live issuance. If no suitable artifact exists, leave live production issuance OUTSTANDING. A new live issuance requires separate human authorization for the synthetic request, issuer assignment, data handling and cleanup; it is not authorized by this assignment. A direct signer check performed by an operator inside the service may avoid key export, but still must be explicitly approved and distinguished from API issuance.
4. Record artifact time, service build, expected kid, verification result and limitations without logging personal data, session tokens, private material or complete credentials. Verify revocation/status separately; cryptographic success alone is insufficient.

Stable public JWKS URL inherited from the supplied baseline: `https://hapis.sfo3.cdn.digitaloceanspaces.com/trust/jwks.json`. It was not re-fetched here.

### Dependency findings: applicability and limits

The [Go vulnerability checker](https://go.dev/doc/security/vuln/) uses call reachability, not proof that an attacker controls the vulnerable arguments. No blanket dependency upgrades were made on the basis of scanner presence alone. The saved JSON contains all 16 symbol-level advisories, including their database descriptions and fixed versions.

| --- | --- |

Inspected runtime queries use parameters and do not exhibit that combination. Production DSN overrides were not inspected. Not a demonstrated SQL injection. |
| `GO-2025-4233`, `GO-2026-5676` (`quic-go`) | HTTP/3/QPACK findings. The server uses `http.Server.ListenAndServe`, not Gin's QUIC/HTTP3 entrypoint. No enabled runtime HTTP/3 listener was found. Scanner interface/error-method reachability is not listener exposure. |

| `GO-2026-5970`, `GO-2026-6629` (`x/text`) | Normalization / PRECIS findings; the latter specifically requires Nickname profile transformation into a short destination buffer. | `GO-2026-6603`, `6610`, `6611`, `6612`, `6617` (`x/net` and/or standard HTTP/2) | Incoming server is plain HTTP/1 as configured; backend HTTP/2 listener exposure was not established. Host findings must not be attributed to production without that evidence; conversely the host scan cannot certify the release image. ## Residual risks, missing verification, and optional work

**Known residual risks:** the two demonstrated authorization blockers; possible historical database-credential compromise pending operator verification; existing stateless access JWTs remain usable until expiry after logout, reuse detection or account disablement (up to 15 minutes). Kratos sessions and application sessions are separate; revoking one does not automatically revoke the other. The canonical session document's broad logout wording should not be read as immediate access-JWT revocation. No new token claims or revocation architecture were introduced. Legacy normalized body/status/validity limitations remain fail-closed. Applicable scanner findings, including outbound HTTP/2 exposure on an unpatched compiler, remain unresolved pending release-toolchain verification.

**Missing verification:** actual production employer/case policies or RLS, legacy schema compatibility, runtime role grants (already outstanding in [the authority deployment security contract](../operations/authority-persistence-v1-deployment-security.md)), live key use, API legacy-verifier wiring, status resolution, runtime mounted-file permissions, credential rotation/reuse, network/firewall configuration, release-image compiler/CA patch status, and infrastructure rate/upload limits. No production credential or log inspection was attempted to fill these gaps.

**Optional future improvements:** none are required merely because a framework/control is absent. Reconsider broad rate-limit/caching/observability changes only with operational evidence and separate scope approval. They do not substitute for resolving the confirmed blockers.

Independent acceptance requires the authoritative authorization decisions and regression coverage, disposition of credential exposure and applicable dependency findings, confirmation that the changes fit the actual deployment schema/configuration, and explicit acknowledgment of remaining live verification. No production deployment or merge is authorized by this report.
